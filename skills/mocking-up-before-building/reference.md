# Mocking up before building: more detail

Read this when the short page is not enough.

## Choosing the form

| The open question | The cheapest mockup that answers it |
|-------------------|-------------------------------------|
| Where do things go? | A rough sketch, in text or boxes |
| What will it look like? | A still picture of the screen in the product's own style |
| How do the steps flow? | A set of pages a person can click through |
| Which version is better? | Two or three versions shown side by side |

Start rough. Move to a more finished form only when the rough one has been agreed.

## Making it honest

- **Use the product's existing look.** Reuse the colours, type and parts the product already has. A mockup in a different style gets approved for the wrong reasons.
- **Check the content against the real data.** Every field shown must exist, or be marked as new. A mockup that shows information the system does not hold promises something that cannot be built as shown.
- **Include the awkward cases**: the longest name, a missing value, a very large number, a list with one item and a list with hundreds.
- **Show it at phone width and at desktop width** if people will use both.
- **The words are part of the mockup.** Headings, button labels, messages and error text are approved together with the layout. Write them as they will appear.
- **Show what each person sees** when different kinds of user see different things.
- **Mark what is not real.** Label sample data as sample data, and say which buttons do nothing.

## Showing it to the owner

- **Say what you are asking.** "Is this the right layout?" gets a better answer than "What do you think?"
- **Look at it yourself first.** Open the mockup and go through every state before the owner sees it.
- **Point out the choices you made for them**, with your reason for each, so they can overrule them.
- **Give your recommendation** when you show more than one version.
- **Change the mockup, not the build**, when they ask for changes. Show the changed version and ask again.
- **Do not start building on "looks fine" about part of it.** List anything they have not yet seen.

## After approval

- **Keep the approved mockup and its approval record** where the project facts file says mockups are kept.
- **Keep the mockup apart from the product's code.** It is a picture to agree on. Do not grow it into the real thing; build the real thing properly.
- **If something cannot be built as shown, stop and say so.** Show the owner the nearest thing that can be built.
- **Compare at the end.** Put the built screen beside the mockup, state by state. List every difference and who accepted it.
- **A matching screen is not a working one.** The mockup proves what was agreed. `proving-it-works` covers whether it works.
