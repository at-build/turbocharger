# Checking the facts

## In short

A note says what was true when it was written. A signal says what it measured. A model says what sounds right. Check each against the real thing before acting on it.

## Use this when

- You are starting a session on work that began earlier.
- A note says something is finished, open, waiting or next.
- A result is about to decide your next step.
- You are about to try again after a failure.
- A model's answer will be saved or shown to someone.

## Do this

1. **Read the note, then look at the real thing.** Check each claim you are about to rely on against the live system.
2. **Correct the note in the same session.** A wrong line left in place misleads the next reader the same way.
3. **Find out what produced a signal and what it measures.** A flag or a count often covers less than its name suggests.
4. **Do not retry a failure that will fail the same way.** If nothing has changed, the result will not. Find the cause first.
5. **Look at real data before building on it.** Read a few dozen real records.
6. **Keep a model's answer only when you can find its evidence.** Ask for the supporting quote, and check the quote is really in what the model was given.
7. **Let the model say "I don't know".** Keep "found nothing", "could not check" and "failed" as different results, all the way to storage.

## Warning signs

- A status quoted from a note that nobody checked.
- "Retry" as the first response to a failure.
- A saved value with no quote behind it.
- One empty value that means both "no" and "could not ask".

## Why it matters

Acting on something untrue produces confident work in the wrong place. The most expensive case is a failure saved as an answer: it looks like a fact from then on.
